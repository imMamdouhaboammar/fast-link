# FastLink Engineering Failure Lessons

This document codifies engineering failure lessons, root causes, and durable invariants extracted during the design, implementation, and evaluation of FastLink navigation acceleration.

---

## [Mobile Touch Gesture Hijack via Unconstrained Pointerdown]

### Context
Browser navigation acceleration in responsive web applications containing anchor tags (`<a>`), accessed across desktop mouse pointers, mobile touchscreens, and trackpads.

### What happened
A naïve pointerdown event listener attached to `document` or anchor elements fired indiscriminately on mobile touchscreen devices when users placed a finger on a link to initiate a vertical page scroll. The application triggered an immediate route transition instead of scrolling.

### Observable symptom
Mobile users were unable to scroll past sections containing dense link lists (such as article feeds or product grids); touching anywhere on a link immediately forced a page jump.

### Impact
Complete breakdown of mobile user experience, 100% bounce rate on mobile devices, and violation of mobile touch-scroll expectations.

### Incorrect assumption
The developer assumed `pointerdown` represents a definitive human intent to click a link across all input device classes.

### Root cause
**Status:** Confirmed  
W3C Pointer Events specification unifies mouse, pen, and touch into `pointerdown`. On touch devices, `pointerdown` fires immediately upon physical screen contact, preceding scroll gesture recognition by several milliseconds.

### Why the architecture allowed it
The event listener failed to interrogate the `pointerType` hardware property of the pointer event before triggering navigation logic.

### Fix
Enforce an inviolable admission gate in the eligibility resolver:
```javascript
if (event.pointerType !== 'mouse') return null;
```
Touch and stylus pointers are unconditionally rejected from early pointerdown navigation and fall back to native browser gesture handling.

### Verification
Simulated pointer events in `skills/fast-link/scripts/verify_gesture_invariants.ts` assert that `pointerType: 'touch'` and `pointerType: 'pen'` return `null` eligibility.

### Prevention rule
Never initiate early navigation on non-mouse pointer events. All pointerdown navigation handlers must strictly enforce `event.pointerType === 'mouse'`.

### Reusable lesson
Unified event APIs across multiple physical hardware modalities (mouse, touch, pen) require explicit input type discrimination before performing irreversible actions.

## [Synthetic Follow-up Click Double Navigation & Analytics Starvation]

### Context
Browser event lifecycle coordination between primary mouse `pointerdown` and the subsequent synthetic `click` event generated by the browser upon mouse release.

### What happened
After early navigation was initiated on `pointerdown`, the browser fired the normal DOM `click` event upon button release. In early prototypes, this either triggered a duplicate navigation request, or when `stopPropagation()` was invoked to silence it, third-party analytics and custom application handlers were starved of click events.

### Observable symptom
Double page requests recorded in server access logs, cancelled network requests in DevTools, or complete disappearance of click conversion events in analytics dashboards.

### Impact
Server resource waste from duplicate SSR requests and corrupted conversion analytics data.

### Incorrect assumption
The developer assumed either that `pointerdown` replaces the `click` event automatically, or that calling `event.stopPropagation()` was the correct mechanism to silence the synthetic click.

### Root cause
**Status:** Confirmed  
The browser specification mandates that a `click` event must be dispatched after `pointerup`. `stopPropagation()` terminates DOM event bubbling, preventing parent listeners (including analytics scripts) from detecting user interaction.

### Fix
Implement a dual-phase WeakSet coordination engine. On `click` capture phase:
1. Verify if the clicked anchor matches the `pendingAnchor` navigated during `pointerdown`.
2. Call `event.preventDefault()` to suppress browser default navigation.
3. Explicitly DO NOT call `event.stopPropagation()`, ensuring the event bubbles cleanly to analytics trackers.

### Verification
Automated assertions in `skills/fast-link/scripts/verify_gesture_invariants.ts` prove `defaultPrevented === true` and `propagationStopped === false`.

### Prevention rule
When intercepting browser navigation via early event phases, always suppress follow-up synthetic clicks using `event.preventDefault()` exclusively; never invoke `event.stopPropagation()`.

### Reusable lesson
Synthetic companion events in browser runtimes must be suppressed at the action level (`preventDefault`), not the notification level (`stopPropagation`), to avoid starving independent observers.

## Rules We Now Enforce for fast-link
- [Every pointerdown navigation listener must enforce `event.pointerType === 'mouse'` to preserve mobile touch scrolling inertia.]
- [Modifier keys (`Cmd`, `Ctrl`, `Shift`, `Alt`) and non-primary buttons (`button !== 0`) must bypass early navigation to preserve native new-tab, new-window, and context menu behaviors.]
- [Follow-up synthetic clicks must be neutralized using `event.preventDefault()` only; `event.stopPropagation()` is strictly prohibited.]
- [Keyboard activation events (`event.detail === 0`) must never be suppressed.]
- [Speculative prefetching must strictly enforce same-origin verification and exclude mutation, auth, or logout routes.]
